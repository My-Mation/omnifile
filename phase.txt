## PHASE 1 — FOUNDATION & APP SHELL
## Objective: A running app with theme system, navigation, file picker,
## and recent files. No viewers yet — picking a file shows its info.
## ============================================================================

### READ FIRST
rules.txt §1–§4.5, §6; ui_rules.txt §1–§9.2 (all component specs),
§13; goals.txt §2, §5.

### BUILD
1. Scaffold Flutter project with the EXACT folder structure from
   rules.txt §4.1. Set app ID, name "OpenFile", dark+light Material 3
   themes from ui_rules.txt §2 (build the full ThemeExtension with all
   color tokens — both themes complete, not stubs).
2. NavigationBar with 3 destinations: Home, Settings, About
   (ui_rules.txt §9.2, §9.3, §9.4). Settings and About are FULLY
   built in this phase (they're cheap and stabilize the shell):

beyond §4.3 list.

- [ ] Pick file → info dialog shows correct name/size/date
- [ ] Picked file appears in recents; swipe removes with UNDO;

- [ ] Airplane mode ON: everything still works
- [ ] flutter analyze: 0 issues

## PHASE 2 — DETECTION ENGINE + TEXT/CODE VIEWER
## Objective: The file-type detection pipeline (unit-tested) and the
## first real viewer. After this phase the app genuinely OPENS files.
## ============================================================================

### READ FIRST
rules.txt §3 (all tiers), §4.4 (detection pipeline — implement in the
exact order given), §5.1, §5.3; ui_rules.txt §8.7, §9.5, §9.7,
§10 (all states); goals.txt §5 (TG1).

### BUILD
1. Domain layer: FileEntity, ViewerType enum, DetectFileType usecase.
   Implement the full pipeline from rules.txt §4.4: extension map →
   magic numbers (ALL listed signatures) → text heuristic → fallback.
   Pure Dart, zero Flutter imports, fully unit-tested.
2. Unit tests: every magic number, every Tier 1 extension, edge cases
   (no extension, `file.pdf.txt`, UPPERCASE.EXT, empty file, 1-byte
   file, file that is a JPEG renamed to .txt — magic must win).
3. Viewer Router: invisible screen that maps detection result → viewer
   (only TEXT/CODE routes to a real viewer now; others route to the
   Unsupported screen from ui_rules.txt §10.4 — this is intentional
   and correct for this phase).
4. Common Viewer Shell (rules.txt §5.1): app bar with overflow menu
   (File info, Share via share_plus, Open with via open_filex,
   theme toggle), loading state (>300ms delayed spinner), error
   state, double-tap fullscreen toggle, state restoration hook.
5. Text/Code viewer per rules.txt §5.3 + ui_rules.txt §9.7:
   - Syntax highlighting via highlight package; extension→language
     map covering the full Tier 1 code list
   - Line-number gutter, current-line highlight, read-only with
     selection/copy
   - Find bar (spec 8.7): match count, prev/next, highlight-all
   - Encoding: auto-detect + manual picker (UTF-8, UTF-16LE/BE,
     Latin-1, ASCII), instant reload
   - Word wrap toggle (default: on for txt/log, off for code);
     font size via pinch (10–28sp, persists) and menu buttons
   - Large files: >2MB loads first 1MB with warning banner + "Load
     more"; >50MB requires confirmation
   - Markdown files: Rendered ↔ Source toggle (flutter_markdown
     rendered view per ui_rules §9.7)
6. Wire recents to store real detected type; Home list now shows
   type-colored file icons (ui_rules §2.4, §6 custom file-icon painter).

### OUT OF SCOPE
All other viewers. Do not stub them with empty screens — route them
to Unsupported.

### ACCEPTANCE CRITERIA
- [ ] `flutter test` passes: detection suite green (all magic numbers,

- [ ] Open a .py/.js/.json/.md/.txt file → correct highlighting,
      gutter, line count
- [ ] Find bar: count correct, navigation works, ESC/X closes
- [ ] Open file saved as UTF-16 → readable; manual encoding switch works
- [ ] 5MB+ text file: warning banner appears, "Load more" appends
- [ ] .md toggles Rendered/Source correctly
- [ ] Rename a .png to .txt → opens as image detection → Unsupported
      screen (with correct info), NOT garbled text
- [ ] Airplane mode: all of the above works
- [ ] flutter analyze: 0 issues; flutter test: all green

### COMPLETION PROTOCOL
Analyze + test + debug build, update PHASE_LOG.md, print checklist,

## PHASE 5 — ARCHIVES & HTML
## Objective: ZIP/TAR/GZ browsing + extraction, and offline-safe HTML
## rendering. This phase contains the app's most security-sensitive
## code — the network-blocking WebView.
## ============================================================================

### READ FIRST
rules.txt §3.3, §5.6, §5.7, §8 (security — read twice);
ui_rules.txt §9.11, §9.12; goals.txt §4 (T1/T2).

### BUILD
1. Archive viewer per rules §5.6 + ui_rules §9.11:
   - Navigable list with breadcrumb bar; folder/file icons by inner
     extension; sizes shown as "2.1 MB → 800 KB"
   - Tap entry → extract to temp cache → open in existing viewer,
     back returns to archive at same position; >50MB entry warning
   - Extract-all: SAF folder picker, ISOLATE-based extraction with
     determinate progress dialog (%, current file, Cancel), success
     snackbar; ZIP-SLIP protection (validate every entry path,
     reject traversal — unit test this with malicious archive)
   - Multi-select mode (long-press) with partial extract
   - TAR, GZ, TGZ handled; encrypted ZIP → clear unsupported message
2. HTML viewer per rules §5.7 + ui_rules §9.12:
   - webview_flutter rendering local file; inject CSP meta
     (default-src 'none') BEFORE load; also intercept and deny all
     external requests at the WebViewClient level (belt AND braces)
   - JS off by default; bottom notice chip "JavaScript off — enable?"
     (session-only enable); even enabled stays network-blocked
   - Relative sibling assets (css/js/img in same folder) served via
     guarded in-app handler — path-traversal tested
   - Rendered ↔ Source toggle (crossfade) with HTML highlighting
3. Archive unit tests: listing, nested paths, zip-slip rejection,
   extraction cancellation mid-stream (partial state cleaned).

### OUT OF SCOPE
RAR/7z (v1.2). Creating archives. Editing extracted files.

### ACCEPTANCE CRITERIA
- [ ] ZIP with 200+ nested entries lists instantly, breadcrumb
      navigation smooth
- [ ] Preview a .txt and a .jpg from inside a zip → correct viewer,
      back preserves position
- [ ] Extract-all with progress + cancel works; cancel leaves no
      partial files
- [ ] Zip-slip test archive (paths like ../../evil.txt) → REJECTED,
      logged, no files written outside target
- [ ] HTML page with external <img src="https://..."> → image shows
      broken placeholder, NO network request (verify: airplane mode
      makes zero difference; optionally verify via device log that
      shouldInterceptRequest denies)
- [ ] HTML with sibling local CSS → styles apply in rendered mode
- [ ] Source toggle shows highlighted HTML
- [ ] Corrupt/truncated zip → error state, no crash
- [ ] Airplane mode: all works; analyze 0 issues; tests green

and interception logic used. Print checklist, STOP.

## Objective: Eliminate dead ends forever. Unknown binaries → hex;

### READ FIRST
rules.txt §3.2, §3.3, §5.8, §5.9, §9; ui_rules.txt §9.13, §9.14,

### BUILD
1. Hex viewer per rules §5.9 + ui_rules §9.13: virtualized 3-column
   layout (offset/hex/ASCII), 64KB lazy chunks with infinite scroll,
   pinned byte ruler, byte-tap tooltip (offset/value/char),
   jump-to-offset dialog, search (hex pattern + ASCII), alternating
   row shading, multi-GB safe.
2. Fallback chain wiring (rules §3.3) — exact order: unknown type →
   text heuristic (>90% printable first 8KB) → text viewer with
   banner → else hex → else Unsupported screen. Every Unsupported
   screen shows info card + [Open as hex] [Open with another app].
   Unit-test the chain: DOC renamed to .xyz → office detection via
   ZIP signature + content-types → docx viewer, not hex.
3. Office best-effort viewers (rules §5.8, ui_rules §9.14):
   - docx: unzip → parse document.xml → headings/bold/italic text

   - pptx: vertical text-slide cards with slide numbers

     text attempt → else graceful unsupported with banner
   - HARD RULE: never crash, never raw-XML-dump. 20 corrupt/mutated
     office fixtures must all land in a defined state.
4. Error-handling hardening pass (rules §9): global error handler →
   in-app error screen; OOM guards on every viewer; verify every
   viewer implements all 4 states (loading/empty/error/content).

### ACCEPTANCE CRITERIA
- [ ] Random binary (.bin of /dev/urandom) → hex view renders

- [ ] Hex search finds both ASCII and hex patterns; jump works
- [ ] Text heuristic: JSON renamed .xyz opens as text with banner

- [ ] All 20 corruption fixtures: defined state each, zero crashes
- [ ] Unsupported screen offers all 3 escape actions; each works
- [ ] flutter test: chain tests + zip-slip + office fixtures green
